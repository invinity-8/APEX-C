# Incident 2026-11-01 – APEX unusable after the first world was created

**Status:** root cause found and fixed in the stability PR. Supabase recovered on its own once the load stopped (project status `ACTIVE_HEALTHY` at 20:05 UTC).

## Symptoms
GM actions took minutes, buttons flickered between enabled/disabled, the spinner was almost always visible,
"Begin Night 1" did not react, players waited long after joining, finally HTTP 504 / connection lost.
Vercel: `Task timed out after 300 seconds` (148×). Supabase: PostgREST and Auth unhealthy, database itself healthy.

| PostgREST logs | `PGRST003 Timed out acquiring connection from connection pool`, 504s on trivial lookups; a `SET statement_timeout` took 14.6 s (CPU starvation on Nano). |
| Postgres | no locks, no long transactions, 2 live sessions, 78 kB game state – the database was overwhelmed by request volume, not by expensive SQL. |
| Vercel runtime errors | `upstream request timeout` from PostgREST, then functions waiting on database calls without a timeout until Vercel killed them after 300 s. |
| Latency per DB round trip (gateway origin time) | before: p50 309 ms / p95 928 ms · storm: p50 1,561 ms / p95 36,000 ms, 203 × 5xx. Function region iad1 (US) vs database eu-west-1 (Ireland). |
| Local reproduction | One GM tab against the mock server: **56 overview requests within one second** on the 20 s poll tick. |

## Root cause
A client-side feedback loop in the GM panel *Players & Access* (it only appears once a world exists, hence the
correlation with world creation – the password creation and world generation themselves were not the cause):

1. `useOnlineGame` built a new `online` object on every render.
2. `PlayersPanel` loaded the overview in an effect that depended on `online`.
3. Every overview call went through the shared `run()` helper, which toggled the global `busy` flag →
   re-render → new `online` → the effect ran again → another overview → …

With a fast server the loop died out after a burst; with a slow database each delayed response restarted it,
so it fed itself until PostgREST's connection pool was exhausted. The same `busy` flag disabled all action
buttons – the flickering buttons and the unresponsive "Begin Night 1".

### Amplifiers
- Every API request did 4–5 sequential REST calls just to authenticate (session, profiles, credential, members, presence write).
- `overview` and `ping` downloaded the full game state.
- No timeout on database calls → hung functions for 300 s instead of a quick 503.
- Function in the US, database in Ireland: ~10 transatlantic round trips per request.

## Fix (stability PR)
- Frontend: stable `online`/`game` identities (`useMemo`), overview polling single-flight every 30 s without touching any busy flag,
  background sync never disables buttons, per-action pending state, single-flight refresh with `since=version`
  ("unchanged" answers), one sequential heartbeat with exponential backoff + jitter, paused while hidden/offline,
  request timeouts and cancellation, request ids for every state-changing action and outcome verification after a lost response.
- Server: authentication in one database call (`apex_authenticate`), presence from the session, `ping`/`state` version checks without
  state transfer, overview in 4 parallel queries without the game state, 8 s timeout on every database call, function `maxDuration` 30 s,
  idempotent commands and world actions (unique `request_id`), privacy-safe timing log per request (`[apex-timing] op status ms db dbMs`).
- Infrastructure: function region `dub1` (next to the database). No Supabase plan change was needed.
